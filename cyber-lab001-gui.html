01 Briefing

Objective. You cannot defend a system you do not understand. Today you build the habit every security engineer needs first: a factual, reproducible baseline of a Linux host — what is running, what is listening, who can log in, and what changed. Today is information-gathering and documentation, not exploitation.

Scenario. You have just been handed a Linux server and told "take care of this." Your first shift should not start with scanning tools. It starts with answering: what is this machine, what does it expose to the network, and what does its current configuration tell me about how it will behave under attack? You will produce a baseline report that a colleague could use to detect future tampering.

Environment

  • Any modern Linux distro (Debian/Ubuntu/Kali — whatever you already run).
  • Tools: ip/ss, ps, systemctl, getent, find, stat, sha256sum, dpkg or rpm, and a text editor. All free, all standard.
  • Working directory: ~/cyber-labs/lab001/ — create it.
  • Note: everything today is read-only. No root required for most tasks; where root helps (e.g. full process visibility), note it in your report.

02 Concept Primer

Read before starting — these three ideas frame every task below.

Baseline
A recorded snapshot of known-good state. Security detection is the art of comparing current state to baseline and explaining every difference.
Listening Socket
A port where a process accepts connections. Every open port is an attack surface — the question is never "is it open?" but "why, and who is allowed in?"
File Hashes
SHA-256 lets you detect modification. Hash once now, compare later. Permissions and ownership on key files decide who can change system behaviour.

03 Tasks — do these in order

Write down every command you run and its key output — your deliverable depends on the evidence, not on the answers. Click a command block to copy it.

1 · Identify the host
Record OS name/version, kernel, hostname, uptime, architecture, and current user → baseline.txt.
mkdir -p ~/cyber-labs/lab001
cat /etc/os-release > ~/cyber-labs/lab001/baseline.txt
uname -a >> ~/cyber-labs/lab001/baseline.txt
hostname; uptime; whoami; arch >> ~/cyber-labs/lab001/baseline.txt
2 · Network posture
List every interface with IP/state, and every listening TCP/UDP socket. Flag 0.0.0.0/:: (anywhere) vs 127.0.0.1 (local only).
ip -brief addr >> ~/cyber-labs/lab001/baseline.txt
ss -tulnp >> ~/cyber-labs/lab001/baseline.txt   # add sudo for full process info
Why this matters
Every listening socket is an attack surface. A service bound to 127.0.0.1 is only reachable from the machine itself; one on 0.0.0.0 is reachable from the whole network. Note any socket whose owning process you cannot identify — that's a finding, not a gap.
3 · Running processes
List all processes with user + command. Name at least five, and flag anything running as an unrecognised user.
ps auxww >> ~/cyber-labs/lab001/baseline.txt
4 · Services
List enabled system services and identify which are network-facing.
systemctl list-unit-files --state=enabled --no-pager \
  >> ~/cyber-labs/lab001/baseline.txt
systemctl list-units --type=service --state=running --no-pager \
  >> ~/cyber-labs/lab001/baseline.txt
Hint: enabled ≠ running
An enabled service starts at boot; a running one is executing now. After a reboot it's the enabled list that defines your real attack surface — a stopped-but-enabled service is a loaded gun waiting for the next boot.
5 · Accounts
List every local user, UID, home, login shell. Mark interactive logins (shell ≠ /usr/sbin/nologin, /bin/false). List UID-0 accounts.
getent passwd >> ~/cyber-labs/lab001/baseline.txt
awk -F: '$3==0 {print}' /etc/passwd   # every account with root powers
6 · Sudo & access control
Which groups exist? Who is in sudo/wheel? What rule could you escalate by? Check /etc/sudoers and /etc/sudoers.d/.
getent group sudo wheel >> ~/cyber-labs/lab001/baseline.txt
grep -rE '^[^#]*ALL' /etc/sudoers /etc/sudoers.d/ 2>/dev/null
7 · File integrity anchors
Pick three security-relevant files (e.g. /etc/passwd, /etc/ssh/sshd_config, one of your choosing). Record permissions, owner, size, SHA-256 → hashes.txt.
for f in /etc/passwd /etc/ssh/sshd_config /etc/shadow; do
  stat -c '%A %U:%G %s %n' "$f"
  sha256sum "$f"
done | tee ~/cyber-labs/lab001/hashes.txt
Why /etc/shadow may fail without root
/etc/shadow is root-only (mode 640). If you can't hash it, note that in your report — "could not read as non-root" is itself a baseline fact. Swap in another anchor like /etc/hosts or /etc/group instead.
8 · Packages
List installed packages with versions (or the top of the list plus a count) — know how to produce it and roughly how large the surface is.
# Debian/Ubuntu
dpkg-query -W -f='${Package} ${Version}\n' | tee ~/cyber-labs/lab001/packages.txt
dpkg -l | wc -l
# Fedora/RHEL (uncomment instead)
# rpm -qa --qf '%{NAME} %{VERSION}\n'

04 Deliverables

Everything lands in ~/cyber-labs/lab001/.

baseline.txt Host identity, network, processes, services, accounts, sudo + a "what surprised me" paragraph
hashes.txt The three integrity anchors with hashes and permissions
report.md One-page markdown: what this host is, its exposed surface, and three concrete risks with one-line rationale each
evidence.png/txt A capture showing at least one command and its output

05 Self-Check

Check yourself honestly — if the answer is no, fix your method before moving on.

Could a colleague with your report.md and hashes.txt detect, six months from now, that /etc/passwd was modified?
Does your report name every listening socket and justify its presence — or at least mark it "unknown, needs owner"?
Do the three risks each reference a specific observation from your baseline — not a generic guess?
