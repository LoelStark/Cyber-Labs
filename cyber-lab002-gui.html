01 Briefing

Learn to enumerate the privilege surface of a Linux host: every place where the system lets one user become another user, run code on a schedule, or inherit elevated rights. This is the exact checklist a security engineer runs during triage, and the exact checklist an attacker runs before choosing an exploitation path. You are not exploiting anything today — you are building the map and learning to reason about each node on it.

A workstation in your org was reported as "acting strangely." Before anyone runs a scanner, you are asked a blunt question: if an unprivileged user on this box wanted root, what would they try first? You cannot answer that from memory — you answer it by enumerating the host's own privilege surface and judging each finding. Your output is a triage note that a senior engineer can act on within five minutes.

02 Concept Primer

Read before starting — these ideas frame every task below.

SUID bit
A file with the setuid bit executes with the permissions of its *owner*, not the caller. `/usr/bin/passwd` is SUID root so you can change your own password entry in a root-owned file. Every SUID-root binary is a potential path to root: either it has a known escape (editors, `less`, `find -exec`, anything that can spawn a shell) or it can be abused to read/write files it should not.
sudoers rules
`/etc/sudoers` and `/etc/sudoers.d/*` grant named users or groups the right to run commands as other users. `ALL=(ALL) ALL` is total. `(root) NOPASSWD: /usr/bin/vim` is *also* total, because `vim` can run shell commands — this is the classic "sudo is not a sandbox" trap.
Persistence via scheduled execution
Anything that runs code on a timer (user crontabs, `/etc/cron.d`, systemd timers, `at` jobs, shell rc files, systemd unit drop-ins) is both a defence problem and an attacker's favourite. The question is always: *who can modify the thing that runs, and as whom does it run?*
PATH hijacking
If a script run as root invokes `curl` without an absolute path, and a directory earlier in root's PATH is writable by you, you supply the `curl`.

03 Tasks — do these in order

Write down every command you run and its key output — your deliverable depends on the evidence, not on the answers. Click a command block to copy it.

1 · SUID/SGID inventory
Enumerate every SUID and SGID file on the system. For each, record path, owner, and whether you can name its legitimate purpose. Produce suid_inventory.txt with a one-line justification per entry, and a total count.
2 · sudo rules
List the rules that apply to you (sudo -l) and the contents of /etc/sudoers plus every file in /etc/sudoers.d/. Flag any rule whose command can spawn a shell, read arbitrary files, or write arbitrary files. Explain why in one line each.
3 · Scheduled execution
Enumerate: your crontab, /etc/crontab, /etc/cron.{d,hourly,daily,weekly,monthly}, systemd timers (systemctl list-timers --all), and at jobs. For each entry, identify the user it runs as and whether that user or a group you belong to can modify the target script.
4 · PATH and world-writable attack surface
Check each directory in root's PATH for group/other write permission. Separately, find files world-writable anywhere under /usr, /etc, and /opt. Count them; list the ten most interesting.
5 · Authentication posture
Read /etc/pam.d/ (at minimum common-auth or the distro equivalent) and /etc/ssh/sshd_config if present. Record: password policy / lockout configuration, whether root login over SSH is permitted, and whether password auth is on.
6 · One hypothesis, written properly
Pick your single most promising finding from tasks 1–5. Write (a) the escalation or persistence hypothesis in five lines, (b) the exact command you would run to confirm it on a machine you are authorised to test, and (c) the log line or artefact that would reveal it had already happened.
