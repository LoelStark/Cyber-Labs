01 Briefing

Lab 001 taught you to observe a host. Today you learn to change one — safely, and with a way back. You will audit a deliberately weak VM configuration, harden it against the attacks you would actually run against it, verify the hardening held, and write a reusable audit script in Bash/Python that a sysadmin could run on any box. Two skills compound here. First, hardening is only real if you can prove it — an unverified change is a rumour. Second, you will write code that encodes the standard, so next month's check is one command, not an afternoon. Security engineering is half knowledge, half automation.

You inherit a small Ubuntu VM that someone provisioned for "quick testing" six months ago. The previous owner is gone. The VM runs a web app and an SSH server, holds a couple of local user accounts, and has never had a security pass. Your manager's requirement: bring it to a defensible baseline, prove the controls work, and leave behind an audit script the team re-runs weekly. You have root (sudo) on this box because you own it. This is a lab VM, not production — if you lock yourself out, you rebuild. That is the whole point: you learn the failure mode where it costs nothing.

02 Concept Primer

Read before starting — these ideas frame every task below.

Attack surface = exposure minus control
The SSH port open to the world is exposure. `PermitRootLogin no` plus key-only auth plus a firewall that only allows your management IP is control. Hardening is not "close everything" — it is making every open thing require something the attacker does not have.
Least privilege is a process, not a file
A service account that can read `/etc/shadow`, a user in the `docker` group (which is root-equivalent by design), a world-writable script in `/usr/local/bin` — each is a privilege path. The audit question is never "is this user admin?" but "what can this identity do that its job does not require?"
CIS benchmarks are opinionated baselines
The CIS Ubuntu Benchmark and the Lynis audit tool encode hundreds of hardening controls. You are not expected to memorize them — you are expected to understand the *categories* (accounts, filesystem, network, logging) and check the ones that matter for this box's actual role.
Verification beats intention
`systemctl status ssh` saying "active" proves nothing about who can connect. You prove hardening by attempting the attack: from another machine (or a second SSH session with a bad key), try the thing the control is supposed to stop. If the attempt fails for the *right reason* (denied by policy, not network down), the control works.
Automation is the force multiplier
A one-time manual hardening pass decays within weeks — config drift, new users, reinstalled packages. The audit script you write today is what makes the baseline durable. It checks; humans fix.

03 Tasks — do these in order

Write down every command you run and its key output — your deliverable depends on the evidence, not on the answers. Click a command block to copy it.

1 · Freeze the current state · Phase 1: Audit before you touch anything (25 min)
Save your Lab 001-style baseline for this VM: ss -tlnp, systemctl list-units --type=service --state=running, users with login shells (getent passwd | grep -v nologin), sudo group members, and the SSH server config (sudo cat /etc/ssh/sshd_config). Put it in baseline-before.txt. You cannot prove improvement without a before.
2 · Run an automated audit · Phase 1: Audit before you touch anything (25 min)
Install and run Lynis (free, open source): sudo apt update && sudo apt install -y lynis && sudo lynis audit system. Save the report. Lynis gives you a warnings/suggestions list ranked by category — this is your real to-do list, cross-checked against your own eyes in step 1.
3 · Write your own audit script, `audit.py`, · Phase 1: Audit before you touch anything (25 min)
that checks the five highest-value items without Lynis: (a) SSH PermitRootLogin, (b) SSH password auth enabled, (c) password aging configured (chage -l for each login user — max days > 90 is a finding), (d) UFW/firewall active with a default-deny posture, (e) any user in docker/sudo/adm beyond root. Each check prints PASS/FAIL/WARN with the evidence line it read. Run it on the un-hardened box — it should FAIL most things. Hint: Read sshd_config with a parser that ignores comments and handles Key=value and Key value forms; grep -v '^#' plus awk '{print $1, $2}' is enough, and subprocess with a whitelist of read-only commands is the Python pattern.
4 · Harden SSH · Phase 2: Harden with a rollback log (30 min)
In sshd_config: PermitRootLogin no, PasswordAuthentication no (ensure you have key-based login working FIRST — add your key before disabling passwords or you lock yourself out), MaxAuthTries 3, X11Forwarding no, ClientAliveInterval 300. Apply with systemctl reload sshd — reload, never restart blind, and validate the config first with sshd -t.
5 · Firewall · Phase 2: Harden with a rollback log (30 min)
Enable ufw, default-deny inbound, allow SSH from your management network only (ufw allow from 192.168.0.0/24 to any port 22 — use your actual management range), allow your web app's port. Verify with ufw status numbered.
6 · Accounts · Phase 2: Harden with a rollback log (30 min)
For every login user: enforce password aging (chage -M 90 -m 7 -W 14 user), disable any account that has never logged in and does not need one (usermod -L + note it), and remove any user from docker/adm groups that does not need them. Document each change and its revert command in changes.log as you go — not after.
7 · (Optional, if time) fail2ban · Phase 2: Harden with a rollback log (30 min)
apt install fail2ban, enable the sshd jail, systemctl enable --now fail2ban, fail2ban-client status sshd. This is detection+response as a service: it converts Lab 004's brute-force insight into an automatic ban.
8 · Re-run `audit.py` · Phase 3: Verify by attacking your own box (20 min)
It should now PASS the items you fixed. Screenshot/pipe the before/after diff — this is your evidence.
9 · Test each control from the attacker's seat · Phase 3: Verify by attacking your own box (20 min)
From another terminal or machine: (a) ssh root@vm → expect Permission denied; (b) ssh -o PreferredAuthentications=password user@vm → expect failure even with the right password; (c) from an IP outside your management range, ssh vm → expect connection refused/timeout. Record what each attempt returned and which control blocked it. Why: a control that blocks you for the wrong reason (network down) is not verified.
10 · Final `changes.log` · Phase 4: The deliverable audit run (15 min)
Every modification with command + revert command, in order. If you can't revert a change, it doesn't belong in a hardening pass on a box you don't fully own.

05 Self-Check

Check yourself honestly — if the answer is no, fix your method before moving on.

`audit.py` output shows real before/after movement on at least 4 of 5 checks.
Your three attacker attempts each fail with a policy denial you can attribute to a specific control — "it failed" is not verification; "password auth rejected by sshd, see journalctl line" is.
`changes.log` has a revert command for every entry, and you could hand this VM to a colleague who could undo your entire pass from that file alone.
The report's "Residual risk" section contains at least one thing you deliberately left unfixed with a reason.
