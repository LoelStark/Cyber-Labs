01 Briefing

Learn the core defensive trade: turn raw logs into detections. You will parse real-format logs (auth.log, web access logs), find an attack buried in them, correlate events across two sources, and write a detection rule that would have caught it automatically. The detection is the deliverable — an analyst who can only read logs is a librarian; an analyst who can write a rule is a detector.

You are the sole security engineer for a small company. At 09:00 Monday, a developer mentions their account "signed out randomly" over the weekend. Nothing else. No alerts — you have no SIEM yet. You have two log files from the weekend: - auth.log — SSH authentication events from the office server - access.log — web server access logs from the same server Your job: find what happened, prove it, and build the detection that should have fired.

02 Concept Primer

Read before starting — these ideas frame every task below.

Logs are event streams, not files
A log file is a sequence of timestamped facts. Your first job is always to parse into structure: time, actor, action, outcome. `grep` reads; Python *analyses*. For anything above one-off questions, write a parser.
The volume vs. the pattern
220 failed logins from one IP is not interesting. 400 failed logins followed by ONE success from the same IP is the whole story. Detection is about *sequences*, not counts.
Correlation across sources
auth.log says the IP got in. access.log says what it did after. One source alone is a rumour; two sources agreeing is evidence. The timestamp is the join key.
Detection rule anatomy
A usable detection has four parts: the *condition* (what pattern in the data), the *scope* (which host/service), the *rationale* (why it means attack), and the *false positive profile* (what legit behaviour looks identical — and how you distinguish it). A rule that fires 50 times a day gets muted; muted rules detect nothing.
Timeline reconstruction
When you write the incident report, order every event by time, mark the source, and separate fact ("at 14:52:01 SSH succeeded for root from 203.0.113.66") from inference ("this was the attacker").

03 Tasks — do these in order

1 · Get oriented · Phase 1: Triage (20 min)
Count the lines in each file, then look at the shape of the data.
wc -l auth.log access.log
   head -5 auth.log
   tail -5 auth.log
Hint
Hint:: Every analyst starts with size and format. You cannot search what you have not sized.
2 · Extract failed logins by source IP · Phase 1: Triage (20 min)
A one-liner gets you 80% of the way: Then do it properly in Python (parse_auth.py): extract timestamp, user, result (accepted/failed), and source IP into structured records. Print the top talkers.
grep "Failed password" auth.log | grep -oP 'from \K[0-9.]+' | sort | uniq -c | sort -rn | head
3 · Find the brute-force window · Phase 1: Triage (20 min)
For the noisiest IP, list the first and last failed attempt and the total count. Is this a human fat-fingering a password, or automation? State your evidence.
4 · Did the noisy IP ever succeed? · Phase 2: Correlation (25 min)
Parse auth.log for accepted logins from that IP. What user, what time, what port? This single line changes the whole investigation — if it is there, everything before it is noise and everything after is post-exploitation.
5 · Join against access.log · Phase 2: Correlation (25 min)
For the 30 minutes after the successful login, what does the web log show from that IP? Write a Python script that merges both sources into one timeline sorted by timestamp. The web log's format differs — parse each format separately, normalize to (time, source, event), then merge and sort.
6 · Reconstruct the attack · Phase 2: Correlation (25 min)
From the merged timeline, write the sequence of events: when did scanning start, when did it escalate, when did the attacker get in, what did they do inside. Note anything that looks like recon (404s on sensitive paths) and the User-Agent that betrays tooling.
7 · Write your first detection · Phase 3: Detection engineering (35 min)
Create detections.yaml with one rule for each of these conditions, in this format: Write three rules: the brute-force-then-success above, a rule for the web recon pattern (multiple 404s on sensitive paths from one IP), and a rule for the tooling User-Agent (python-requests hitting admin paths).
- id: BRUTE-FORCE-SSH-001
     title: SSH brute force followed by success from same source
     scope: auth.log / office-server
     condition: >-
       count of "Failed password" events per source IP within 10 minutes >= 20
       AND an "Accepted password" from the same IP within 15 minutes after
     rationale: Password spraying/brute force that succeeded is a compromise, not noise.
     false_positives: Legit users mistyping, password managers — distinguish by count and
       success correlation; a single typo never looks like 400 failures.
     severity: high
8 · Make one rule executable · Phase 3: Detection engineering (35 min)
Write detect.py that takes a log file and prints an alert when a condition fires, in the format [ALERT] <rule id> <time> <summary>. Run it against the synthetic logs and capture the output.
9 · Backtest · Phase 3: Detection engineering (35 min)
Run your detection against the FIRST 20 minutes of logs (before the attack). It should print nothing. If it fires, your rule has false positives — tighten the threshold and say why in a comment. A rule that cannot stay quiet on clean data is not a rule.
10 · Write the incident report · Phase 4: Response (10 min)
from the template below. End with a concrete containment action: what would you actually DO right now, in order?

06 Assessment

Answer in writing. Draft here, then copy into your report.

Q1The attacker used 220 invalid-user failures and 180 root failures before succeeding. Why do attackers bother with "invalid user admin" at all, when "root" is guaranteed to exist? What does the mix of both tell you?
Q2Your brute-force rule thresholds at 20 failures in 10 minutes. A legit employee with a password manager on a flaky VPN could generate failures. What extra condition in the rule kills that false positive without weakening the real detection?
Q3You have the attacker IP. Why is blocking the IP the weakest containment action, and what should come first?
Q4The web log User-Agent is `python-requests/2.31`. Why is that a strong indicator here and a weak indicator in general? What else would you check before calling it the attacker?
Q5If you had a real SIEM (Splunk, Elastic, Wazuh), how would this lab change? What would you gain, and what would you lose versus a 90-line Python script?
